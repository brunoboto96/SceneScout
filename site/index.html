!New quest: scout your app

Your coding agent, turned into a QA tester for any web app.

SceneScout explores your running app the way a careful tester would: it clicks, fills forms, switches roles and calls the API behind a hidden button. Then it tells you what is broken and what could be better, with a picture and the evidence for every line.

Try it on an app you are allowed to test. No account, no API key:
npx -y scenescout http://localhost:3000
It opens pages and follows links, sends no form, and writes a short report to scenescout-report/ in the current folder.

The tour

Every feature, in under eight minutes.

Read the transcript

1. Meet SceneScout

This is SceneScout. It turns the coding agent you already use into an exploratory tester, for any web app. Scripted end-to-end tests answer one question. Does this exact flow still work? They say nothing about the rest of the app. SceneScout explores the whole app, like a curious, thorough tester. It clicks, fills forms, switches roles, and reports what's broken, and what could be better. Your coding agent is the brain. SceneScout gives it a real browser, deterministic checks and a memory, over MCP. No extra model, and no extra API key. It works with Claude Code, Cursor, VS Code, Codex, Gemini, Copilot, Windsurf, and any other MCP client. Next, a first look, in one command.

2. A first look in one command

Let's try it. Harbor is a small demo order desk, with bugs planted on purpose. One command takes a first look at any app you're allowed to test. No account, no API key, and no setup. A first look runs in observe mode. Only reads leave the page, so nothing on the site can change. Thirteen seconds later, it has measured twelve pages, and it leads with the three problems to look at first. So what does it look for?

3. What it catches

Here's what it caught on Harbor. On the dashboard, a badge covers the All orders button. SceneScout measures that from the layout boxes. No screenshot guessing. And the weekly chart never loads. Its request answered 404. Filter the orders by archived, and the server fails with a 500. The page just shows an empty table. It tells the user there's nothing there. A hidden button proves nothing. SceneScout calls the app's own API, as each role. Here, a clerk approved an order the page hid from them, and the server said yes. Like an impatient user, it double-clicks. Create order sent the same request twice, and made two orders. On every page, after every action, it checks for broken layout, real breakage, permission leaks, and pages that lie, saying saved, after the server refused. It scores accessibility and craft from 0 to 100, counts the steps a task takes, and sniffs out security smells, like typed markup that comes back as an element. Now let's give it to your agent.

4. An exploratory run

For a deeper run, hand it to your coding agent. Just ask. Use SceneScout to test your local address. In Claude Code, there's a slash command too. With no flags, a guided form asks in plain words. The address, what to check, how you sign in, how careful to be, and how thorough. Look only is the default. A care level that writes on a remote site, or creates test data, needs your yes, in a second form. The agent can't answer that one for you. While it runs, a live view on your machine shows every agent. What it's doing, the page it's on, and a feed of every action. Bigger apps split into lanes. Here, three agents test the demo in parallel, each with its own role, and their findings merge into one report. The report opens with a plain summary. What was checked, what was found, and each problem, with its steps, what was expected, and what happened. Developers get the technical details, folded underneath. The evidence, the repro trace, and a Playwright regression test, ready to fill in. At the end, problems come back as plain cards, worst first. Mark one not a bug, and it's remembered, so it never comes back as new. To share it, make a team report. A cover, every problem with its picture, what wasn't checked, and blank sign-off lines. File problems as GitHub or Jira tickets. You see a preview first, nothing is filed until you say yes, and filed tickets are read back later. After a fix, re-check tests the same problems again, and never less carefully than before. And a check you like can be saved by name, and run again. Next, evidence you can hand to anyone.

5. Automated QA with evidence

Now, the journeys that must never break. Save the journeys that matter as a few lines of JSON. The happy paths, and the ones that must fail politely. Write them by hand, or keep one your agent just walked. scenescout check replays them with no model involved. It measures every page, and fails only on what it can prove. Recorded, every run leaves proof. The replay page shows each journey, with a pass or fail badge, and the page after every step. A broken journey opens at the step that broke. Step three expected a 200, and the server answered 500. Each journey is filmed too, so a pass is something you can watch. Here, placing an order. And a test report, laid out by your own template. Test IDs, the requirements each covers, expected and actual results, and a screenshot per step. Every deviation is listed again for the reviewer, and every piece of evidence has its fingerprint. SceneScout signs nothing. The sign-off lines are left for your people. Next, the same gate, in your CI pipeline.

6. In CI and on pull requests

All of this works in CI, as well. There are five commands for CI. A gate, an unattended run, QA from a pull request comment, filing issues, and a preflight. As a GitHub Action, the gate is a few lines. It runs on every pull request, keeps its evidence, and writes SARIF for code scanning. scenescout ci runs an unattended exploratory session, with the Anthropic or OpenAI API, split into lanes. It reports, and never fails the build. Or comment on a pull request. /scenescout qa tests the preview, and replies in the thread. Ask it to compare the save button, and it highlights the pixels that changed. scenescout preflight checks in seconds, with no browser, that the runner can reach the app, the saved sign-in, and the model's API. And scenescout export files the findings as GitHub or Jira issues, each one only once. And all of it is safe by default.

7. Safe by default

Now, safety. Every request the page sends is judged against the session's write mode. Observe, read-only, safe-write, or destructive. The agent is told never to choose destructive itself. A refused request never reaches your server. The page gets a refusal instead, and if it still says saved, that's a finding too. Not sure? scenescout policy explain shows how any one request would be judged, in every mode, and which rule decides it. A team can commit a config file that caps what any agent may choose, refuses every outbound path, or masks emails and card numbers. And there's no telemetry. Finally, how it gets better with every run.

8. Smarter every run

Finally, what makes it get better. SceneScout remembers. Each run starts from what the last one learned, and re-tests the bugs that earlier runs left open. Done is a contract. The report lists everything not tested, and at the extensive level, it won't finish while any known page is unvisited. And it's measured, not asserted. Every change is scored against an app with thirteen planted bugs, and a held-out app it's never tuned on. Behind a sign-in? Sign in once yourself, SSO and MFA included, and every session reuses it. In Chromium, Firefox, or WebKit. Rather press buttons than write prompts? The Claude Code mod adds a guided panel, and the Claude Desktop extension needs no terminal at all. SceneScout is free and open source. Install it with one command, and let your agent find the bugs, before your users do. Thanks for watching.

The bestiary

It finds what a person would notice, and what they wouldn't.

As it explores, it checks for these, and files each one with the steps to repeat it.

Broken layout

Buttons hidden under a sticky bar, controls that overlap, text pushed off screen. Measured from the page itself, so nothing is guessed from a picture.

Things that break

Errors, crashes, failed requests, broken images and pages with no way out.

Permission leaks

It calls the app's own API as each role, so "the button is hidden" becomes "the server refuses it", or doesn't.

Pages that lie

"Saved!" after the server refused the save, or an empty table after the request behind it failed.

Impatient users

A double-click that sends the same order twice, the bug real people find first.

Hard to read, hard to use

Low contrast, missing labels, tiny targets, no visible focus, and how many steps a task really takes.

Choose your class

One run, read two ways.

The same report opens in plain words for the people who need to know what is wrong, with the detail one click away for the people who will fix it.

The Seer

For QA, product and anyone who doesn't open a terminal

Every problem is written as what was done, what was expected and what happened, with a picture of the page.

  • Visible problems shown, not described: the covered button, the broken image, the text too faint to read.
  • Saved journeys recorded step by step, as pictures and video, so a pass is something you can watch.
  • A test report laid out by your own template, with expected and actual results and sign-off rows.
  • Findings filed straight into GitHub or Jira, each one once.
The Artificer

For developers

Every finding carries the request that failed, the steps that led to it, and a test to keep it fixed.

  • Runs from the agent already in your editor: Claude Code, Cursor, VS Code, Codex, Gemini CLI and more.
  • Next to the source, it names the file behind the bug and a likely fix.
  • A Playwright regression-test skeleton for every finding.
  • A deterministic gate for pull requests, with code-scanning results.
The quest log

QA you can hand to someone, with the proof attached.

Save the journeys that matter, the happy paths and the ones that must fail politely. Every pull request replays them, with no AI involved, and keeps the evidence.

  1. Save a journey

    A few lines describing a task: open the form, fill it in, expect the order to be created.

  2. Replay it on every change

    The check runs it in a real browser and fails the pull request when a step breaks.

  3. Keep the evidence

    A picture after every step, a video of each journey, and a test report anyone can read.

Summon a scout

Ask for it on any pull request.

Type a command in a comment and SceneScout answers in the thread, with pictures taken by a real browser.

  • /scenescout qaExplores the pull request's preview and replies with what it found.
  • /scenescout qa show the Save buttonReplies with a picture of that element.
  • /scenescout qa compare the Save buttonPictures it on the base and on the pull request, with the changed pixels highlighted.
  • /scenescout qa checkRuns your saved journeys on the branch and replies with each one's result. The video of every journey is in the run's files.

The preview commands test a deployed preview, so the pull request's code never runs beside the model's key. qa check runs your own workflow on the branch and uses no key at all. Set it up.

Your party

Watch it work, or read along later.

Each run opens a live view on your machine: one card per agent, the page it is on, and every action it took.

Begin your quest

Start in three steps.

You need Node 20 or newer and an app you are allowed to test.

  1. 1

    Install it for your agent

    One command sets up the server, the testing method and the test browser.

    npx -y scenescout install                    # Claude Code
npx -y scenescout install --client cursor    # or vscode, codex, gemini, copilot, windsurf

    Prefer an app? The Claude Desktop extension installs with a double-click from the latest release.

  2. 2

    Start your app, then ask

    In a new chat with your agent:

    Use SceneScout to test http://localhost:3000

    Not sure what to say? In Claude Code, type /scenescout and it asks four plain questions instead.

  3. 3

    Read the report

    It lands in .scenescout/report.md, opening with each problem in plain words. Add a check to your pull requests when you want it on every change.

The zones

Safe by default, enforced where it counts.

The rule sits on the network, not in an instruction to the AI. A blocked request never reaches your server.

Sanctuary observe

Page loads and signing in. Forms that post are refused.

Default for a first look, and for an agent on a remote site
Town read-only

Forms can be sent, and can create a record or change one. Deletes and edits by PUT or PATCH are refused.

Default for the check, and for an agent on a local app
Frontier safe-write

Creates records. PUT, PATCH and DELETE only on the ones it created.

The Wilds destructive

Everything. Only when you say the data is disposable.

Only HTTP is checked: messages over a WebSocket are not, and a link that acts when opened, such as an unsubscribe link, is followed. Only test sites you own or are allowed to test. How the safety model works.
